# 06 · 开发日志（DEVLOG.md）

## 目的

`DEVLOG.md` 记**人的输入、判断与方向**，不记代码实现细节。
技术实现看 `README.md` 的版本历史；编码约定看 01–05。

**读者是用户本人**：他打开文件第一屏就要知道「现在到哪了、下一步做什么、为什么这么选」。

## 何时写（四条，覆盖绝大多数情况）

| 触发 | 处理 |
| --- | --- |
| 用户提出新需求 / 改变方向 | **必记**一条 |
| 用户做出选择（选 A 不选 B） | **必记**一条，写清被放弃的那条 |
| 用户报告问题 / 表达不满 | **必记**一条，问题现象原样保留 |
| 纯技术问答、无方向性 | 记一条 `[仅讨论]`，可与同会话合并 |

⚠ **只在 act 模式写文件**。plan 模式只讨论；等用户切到 act 并有结论后补记。
⚠ 用户说「记一下日志」时，无论当时什么模式：plan 模式下先答应并说明「切 act 就写」，
切到 act 后立刻补记（这是少数允许跨越模式承诺的事项）。

## 写在哪

1. `DEVLOG.md` → `## 会话记录` 区**最上方**插入新条目（新的在最上面）；
2. 同步更新顶部三个区：
   - `## 当前状态` —— **覆盖式更新**，不是追加；
   - `## 待办与方向` —— 勾掉已完成的、补新的；
   - `## 已放弃 / 已回退的方案` —— 只有出现新的放弃项才加行。

## 条目模板

    ### YYYY-MM-DD HH:MM　一句话标题

    **我说**（原话）
    > 逐字引用，不润色

    **意图**
    用户的真实诉求（推断的标 `推断：`）

    **决定 / 过程**
    - 做了什么、为什么这么选

    **代价 / 风险**
    必填。没有代价就写「无已知代价」

    **待办**
    - [ ] ...

## 硬性要求

- **用户原话放引用块**，**不改写成「用户想要…」**；长消息取关键句，但保留原语气与用词。
- **推断与事实分开**：拿不准的写 `推断：`。
- **每条必须有一行代价 / 风险**（尤其是贪心的方案）。
- **只追加、不改写历史**；发现记错了补一条 `[更正]`，不回头改旧条目。
- **单个条目 ≤ 30 行**，超了只留结论 + 指向对应的 README 章节。
- 事件发生在建日志之前、事后补记的，标 `[追溯整理]`，时间可近似。

## 不写什么

- 密钥、令牌、密码 → 写 `[已脱敏]`；
- 完整代码 diff / 大段源码 → 指向 `README` 或 git 提交；
- 大段报错原文 → 只留一行摘要 + 指向 `<项目根>\.logs\_error.log`；
- AI 的长篇解释 → 浓缩成 1–3 句。

## 体积控制

- 文件超过 **600 行**时，在回复里提示用户「该归档了」，建议把最早的季度整段移到
  `docs/devlog/<年>-Q<n>.md`，`DEVLOG.md` 只留近两季。
- **不要自行归档**，等用户确认。

## 编码

UTF-8 无 BOM、**LF**（`.gitattributes` 的 `*.md` 规则已覆盖）。
写完按 04-workflow 的编码检查复查一次。
